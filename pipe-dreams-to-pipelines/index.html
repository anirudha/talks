Your agent is not
a microservice.

A microservice does one thing and reports one outcome. An agent decides what to do, at runtime, differently every time — and then reports 200 OK either way.

What RED metrics will never tell you

Three failures with a healthy dashboard.

Failure 01
It answered wrongly
The tool returned order_not_found; the model narrated a delivery date anyway. Latency normal, status 200.
needs → the tool result and the output text on the same trace
Failure 02
It took the long way round
Eleven model calls where two would do, because a tool description changed and the agent kept re-planning. P50 barely moves. The bill triples.
needs → span count and gen_ai.usage.* per trace
Failure 03
It got quietly worse
A prompt tweak drops tool-selection accuracy from 82% to 64%. Nothing errors, nothing alerts. You hear it from a support ticket.
needs → a graded dataset run on every change

None of these are new observability problems. They are the same problems one level down — at the span, not the request. The tools you already run can see them, once the spans carry the right attributes.

One question. One trace.
22
spans per turn · 5 questions → 110 spans

A single user question fans out into a plan, a delegated sub-agent, three tool calls, two MCP round trips, and a synthesis step. That is a distributed system inside one HTTP request — and only 2 of those 22 spans carry token usage, because only the model calls do.

Which is the whole argument for tracing rather than logging: you cannot reconstruct a 22-span decision tree from print statements, and you should not try.

The thing that makes all of this portable

OTel GenAI semantic conventions.

Not an OpenSearch schema — an OpenTelemetry one. Any framework emitting spans with these attributes becomes queryable the same way, and that is the only thing we ask of your agent today. The condition is worth saying out loud: the Agent Traces view surfaces spans carrying gen_ai.operation.name.

AttributeCarriesWhat it unlocks downstream
gen_ai.operation.namechat · invoke_agent · execute_tool · embeddingsSpan category. This is the attribute the Agent Traces list filters on.
gen_ai.agent.nameWhich agent or sub-agent ran this stepPer-agent RED once the collector promotes it to a label.
gen_ai.request.modelThe model actually calledCost and quality attribution by model, no bespoke metric.
gen_ai.usage.input_tokens / output_tokensToken counts, per model callToken spend as a first-class signal beside latency.
gen_ai.tool.name + .call.arguments / .resultWhat the agent called and what came back"The tool said no and the model said yes" — visible on one span.
gen_ai.conversation.idSession, across turnsStitch a multi-turn conversation out of separate traces.

Why two stores and not one

Spans have unbounded cardinality — every trace ID, tool argument and session is unique. That is a search-engine workload. RED metrics are small, dense and queried over long windows: a TSDB workload.

How they meet

Not a federated query engine — nothing joins a Prometheus series to an OpenSearch document in one query. The UI routes per signal and correlates on trace ID and service name — enough to walk a spike to the exact span.

Deterministic tools on purpose: when the eval in Lab 05 fails, you want to know the agent was wrong, not that a third-party API was flaky. Save the flakiness for production.

Lab 01 · step 1 · register

One call wires the whole pipeline.

# pip install "opensearch-genai-observability-sdk-py[anthropic]"
from opensearch_genai_observability_sdk_py import register, observe, enrich, Op

register(
    endpoint="http://localhost:4318/v1/traces",
    service_name="acme-support-agent",
    # auto_instrument=True by default — it discovers installed instrumentors
)
register() configures the tracer provider, the OTLP exporter and auto-instrumentation in one call. Everything after this line is either a decorator or a label.

Pass the endpoint explicitly in the lab so you can see it. In production this line does not change — you set OTEL_EXPORTER_OTLP_TRACES_ENDPOINT and let the environment decide.

Lab 01 · step 2 · decorate

Two decorators. Whole run stitched.

# the entry point — one invoke_agent root span per turn
@observe(op=Op.INVOKE_AGENT, name="acme-support-agent")
def handle_support_question(question: str, conversation_id: str = "anonymous") -> str:
    enrich(session_id=conversation_id)   # → gen_ai.conversation.id
    return run_turn(question)          # your existing loop, untouched

# a tool — arguments and return value captured for you
@observe(op=Op.EXECUTE_TOOL, name="lookup_order")
def lookup_order(order_id: str) -> dict:
    return _ORDERS.get(order_id) or {"error": "order_not_found"}

name= on an EXECUTE_TOOLgen_ai.tool.name
nothing — the argumentsgen_ai.tool.call.arguments
nothing — the return valuegen_ai.tool.call.result
enrich(session_id=…)gen_ai.conversation.id
Lab 01 · step 3 · auto-instrumentation

The model calls traced themselves.

You decorated two functions. You got a tree.

Nothing in Lab 01 wrapped a model call — and yet every chat span, its model name, its token counts and its stop reason are on the trace. That is the instrumentor for whichever client library you installed, picked up by register().

Opt in with the extra that matches your stack

  • [bedrock] — Bedrock converse with toolConfig
  • [anthropic] — messages.create with tools
  • [openai] — chat completions and the OpenAI Agents SDK
  • [langchain] — LangChain and LangGraph, callback handler auto-registered
  • [all] — a multi-framework agent

Two honest caveats, so you are not surprised later

Auto-instrumentation is opt-in and Python-first. You install the extra; nothing is magic about the base package.

The TypeScript SDK is a function wrapper, not a decorator — observe({op}, fn), with await register() — and its coverage is narrower than Python's today. Instrumentation in Node is fine; the scoring side in Lab 05 is Python.

If you brought your own agent

Do that instead. Add register() and one @observe(op=Op.INVOKE_AGENT) on your entry point, point it at localhost:4318, and rejoin at Lab 02. Everything downstream is attribute-driven, so it does not care whose agent it is.

Lab 02 · step 1 · the Collector

One receiver. Two pipelines.

otel/collector.yaml — open it and read it now, because this is the file you will edit in your own stack. 

receivers:
  otlp:
    protocols: { grpc: { endpoint: 0.0.0.0:4317 }, http: { endpoint: 0.0.0.0:4318 } }

exporters:
  otlp/dataprepper:                       # traces → Data Prepper → OpenSearch
    endpoint: data-prepper:21890
    tls: { insecure: true }
  prometheus:                             # metrics → scraped by Prometheus
    endpoint: 0.0.0.0:8889
    resource_to_telemetry_conversion: { enabled: true }

service:
  pipelines:
    traces:  { receivers: [otlp], processors: [batch], exporters: [otlp/dataprepper] }
    metrics: { receivers: [otlp], processors: [batch], exporters: [prometheus] }

resource_to_telemetry_conversion matters most and gets the least attention — it turns resource attributes into Prometheus labels, which is what makes by (service_name) work.

Lab 02 · step 2 · Data Prepper

One entry. Two sinks. Two index patterns.

entry-pipeline:
  source: { otel_trace_source: { ssl: false } }        # :21890
  sink:
    - pipeline: { name: raw-pipeline }
    - pipeline: { name: service-map-pipeline }               # same spans, twice

raw-pipeline:                                   # the spans you query in Lab 04
  source: { pipeline: { name: entry-pipeline } }
  processor: [ { otel_traces: } ]
  sink: [ { opensearch: { hosts: [https://opensearch:9200],
                     index_type: trace-analytics-raw } } ]

service-map-pipeline:                           # the topology in Lab 03
  source: { pipeline: { name: entry-pipeline } }
  processor: [ { service_map: } ]
  sink: [ { opensearch: { hosts: [https://opensearch:9200],
                     index_type: trace-analytics-service-map } } ]
This is the answer to "who drew the service map?" — nobody did. service_map derives caller/callee edges from parent-child span relationships and writes them as their own documents. A sub-agent you add tomorrow appears the first time it serves a request.
Lab 02 · step 3 · what landed

Two index patterns, different jobs.

$ curl -s "localhost:9200/_cat/indices/otel-v1-*?v&h=index,docs.count,store.size" index docs.count store.size otel-v1-apm-span-000001 347 1.1mb otel-v1-apm-service-map 9 48.4kb
Index patternOne document isYou use it for
otel-v1-apm-span-*One span — with all its gen_ai.* attributes, its traceId and its parentSpanIdTrace trees, PPL over reasoning, token attribution, span-level evals
otel-v1-apm-service-mapOne caller→callee edge, with hashed IDs and the target resourceThe Application Map, and the dependency view that separates errors from faults

Note the ratio: 347 spans produced 9 edges. Topology is tiny and slow-changing; spans are large and fast-growing. That asymmetry is why they are separate indices with separate retention — and the first knob you will turn when the bill arrives.

Lab 02 · step 4 · the bridge

Span attribute → Prometheus label.

This single rename is why you can write by (gen_ai_agent_name) in PromQL and by attributes.gen_ai.agent.name in PPL and mean the same thing.

On the span (OTel)In PrometheusWhy the rename
gen_ai.agent.namegen_ai_agent_nameDots are illegal in Prometheus label names, so the exporter maps them to underscores.
gen_ai.request.modelgen_ai_request_modelSame rule. This is a convention, not an OpenSearch choice.
service.name (resource)service_nameOnly present because resource_to_telemetry_conversion is enabled.
gen_ai.conversation.iddeliberately not promotedUnbounded cardinality. It belongs on a span, never on a time series.
The trap Wolfgang will make you look at

Promoting one high-cardinality attribute to a label is how a Prometheus instance falls over. agent name and model are bounded — tens of values. conversation id, user id, order id and tool arguments are not. Put those on spans, where unbounded cardinality is the storage engine's entire job.

Lab 02 · step 5 · the metrics side

The GenAI metric families, for free.

$ curl -s localhost:9090/api/v1/label/__name__/values | jq -r '.data[]' | grep gen_ai gen_ai_client_operation_duration_bucket gen_ai_client_operation_duration_count gen_ai_client_operation_duration_sum gen_ai_client_token_usage_bucket gen_ai_client_token_usage_count gen_ai_client_token_usage_sum

Lab 03 · step 3 · RED in native PromQL

Rate. Errors. Duration. Per agent.

# rate — invocations per second, per agent
record: acme:agent_requests:rate5m
expr:   sum(rate(gen_ai_client_operation_duration_count[5m])) by (gen_ai_agent_name)

# errors — error ratio, per agent
record: acme:agent_errors:ratio5m
expr:   sum(rate(gen_ai_client_operation_duration_count{error_type!=""}[5m]))
        by (gen_ai_agent_name)
      / sum(rate(gen_ai_client_operation_duration_count[5m]))
        by (gen_ai_agent_name)

# duration — p95 latency, per agent
record: acme:agent_latency:p95_5m
expr:   histogram_quantile(0.95,
          sum(rate(gen_ai_client_operation_duration_bucket[5m])) by (le, gen_ai_agent_name))

# and the one RED never had — cost, per agent, per model
record: acme:agent_output_tokens:rate5m
expr:   sum(rate(gen_ai_client_token_usage_sum{gen_ai_token_type="output"}[5m]))
        by (gen_ai_agent_name, gen_ai_request_model)

Two more rules make these page: p95 over 4 s for 5 minutes, error ratio over 5% for 10 minutes. Paste them in at localhost:9090 and watch them evaluate against your own traffic.

A word from someone who runs this at scale

What changes at a hundred agents.

Six containers on a laptop hide three problems that arrive the moment this is real. All three are Collector-side decisions — one config, not a hundred agent redeploys.

01
Volume
22 spans per turn is a multiplier
A request that was one span is now twenty. Sample at the trace level, never the span level — a half-sampled chain reads as a complete one that made no sense.
knob → tail sampling
02
Cardinality
Labels are a budget, not a feature
Every promoted attribute multiplies series. Bound the set deliberately — agent, model, operation, service. User, session and order IDs stay on the span.
knob → label allowlist
03
Content
Prompts are payloads
Tool arguments and model output are the fields most likely to carry customer data. Decide capture policy before you turn it on.
knob → redaction processor

Lab 04 · step 0 · the shape of every query

Four verbs. That is the language.

source = otel-v1-apm-span-*        // where to read
| where  …                          // narrow
| stats  … by …                     // aggregate
| sort   - …                        // order

If you have written a shell pipeline you already know this. The reason it matters here: agent questions are ad hoc by nature. You will not have a dashboard for "did any trace call the same tool more than three times" until the day you need it, and then you need the answer in thirty seconds.

Run these in Observability Stack → Logs, or on the Agent Traces page. Both give you the same editor over the same index.

Lab 04 · query 1 of 4

Replay one turn's trajectory.

| where traceId = 'c30d4f1…'
| fields startTime, attributes.gen_ai.operation.name,
         attributes.gen_ai.tool.name,
         attributes.gen_ai.usage.output_tokens, durationInNanos
| sort startTime

The same tool, four times, 12 ms each — and five model calls around them. The tool was never slow. The agent would not accept the answer. That is a prompt bug, and no latency dashboard points at it.

Lab 04 · query 2 of 4

Where the money goes.

// token spend by agent and model
source = otel-v1-apm-span-*
| where isnotnull(attributes.gen_ai.request.model)
| stats sum(attributes.gen_ai.usage.input_tokens)  as in_tokens,
        sum(attributes.gen_ai.usage.output_tokens) as out_tokens,
        count()                                     as calls
  by attributes.gen_ai.agent.name, attributes.gen_ai.request.model
| sort - out_tokens

isnotnull on the model field is doing real work — it is what selects only the model-call spans out of the 22. Tool and agent spans have no token usage, and summing over them would silently divide your averages by ten.

Same question on the metrics side: sum(rate(gen_ai_client_token_usage_sum{gen_ai_token_type="output"}[5m])) by (gen_ai_request_model). PPL finds which trace; PromQL watches the trend.

Lab 04 · query 3 of 4

Which tool is letting you down.

// failure rate per tool — the number no service dashboard has
source = otel-v1-apm-span-*
| where attributes.gen_ai.operation.name = 'execute_tool'
| eval failed = if(status.code = 2, 1, 0)
| stats count()      as calls,
        sum(failed) as failures,
        avg(durationInNanos) / 1000000 as avg_ms
  by attributes.gen_ai.tool.name
| eval failure_pct = round(failures * 100.0 / calls, 1)
| sort - failure_pct

A tool that fails 30% of the time is not necessarily broken — it may be getting bad arguments from the model. gen_ai.tool.call.arguments is on the same span, so the next query writes itself: filter to the failures and read what the agent actually passed.

Lab 04 · query 4 of 4

The loop detector.

Fourteen lines of PPL that catch the failure mode that costs the most and alerts the least. 

// traces where the agent kept re-planning
source = otel-v1-apm-span-*
| where attributes.gen_ai.operation.name = 'chat'
| stats count() as chat_steps,
        sum(attributes.gen_ai.usage.output_tokens) as out_tokens
  by traceId
| where chat_steps > 3
| sort - chat_steps
traceId chat_steps out_tokens c30d4f1… 5 2845 8b71ee0… 2 740 4f2c9ab… 1 420

Your specimen trace is at the top. Five model calls and 2,845 output tokens to fail at answering one question — roughly four times the cost of the two that succeeded. Save this query. It is the cheapest agent alert you will ever write.

Starters, easiest first

Three things that will trip you

Field names keep their dots in PPL. attributes.gen_ai.usage.output_tokens, not underscores. The underscore form is the Prometheus side.

Duration is durationInNanos. Divide by 1,000,000 in an eval so the column header stays readable.

Status code 2 means error in OTel, not 500. status.code = 2 is your failure predicate.

Green sticky when

  • You wrote one query of your own that returned rows. Any query. Wrong answers count — a syntax error does not.

Lab 05 · step 1 · define the golden path

What should have happened.

evals/dataset.py — a golden path is not an expected string. It is the expected sequence of decisions, plus a budget. 

CASES = [
    {
        "id":             "order-missing",
        "question":       "where is order A-9999?",
        "golden_tools":   ["lookup_order"],          # once. not four times.
        "must_contain":   ["could not find", "check the order number"],
        "must_not_contain":["shipped", "arrive", "delivery"],  # no invented facts
        "max_chat_steps": 2,
        "max_output_tokens": 600,
    },
    ...
]
Four criteria, four different kinds of wrong. golden_tools catches bad tool selection. must_not_contain catches confabulation. max_chat_steps catches looping. max_output_tokens catches the cost regression that nobody notices until the invoice.
Lab 05 · step 2 · score, in the same trace

A score is another span attribute.

from opensearch_genai_observability_sdk_py import observe, score, Op

@observe(op=Op.INVOKE_AGENT, name="acme-support-agent")
def run_case(case: dict) -> str:
    answer = handle_support_question(case["question"])
    trace  = collect_trace()                 # spans from this run

    score(name="tool_path_match",  value=path_match(trace, case["golden_tools"]))
    score(name="no_confabulation", value=absent(answer, case["must_not_contain"]))
    score(name="step_budget",      value=chat_steps(trace) <= case["max_chat_steps"])
    return answer

The scores ride the same OTLP pipeline from Lab 02 and land on the same spans from Lab 04. No second datastore, no eval warehouse, no CSV export — so "why did this case fail?" and "what did the agent do?" are one click apart, not one team apart.

Name it correctly, it will save you an argument

Agent Evals is the SDK side — score(), evaluate(), Benchmark — and score(value=…) is an unbounded float, so there is no pass/fail primitive here. Agent Health is a separate product on localhost:4001; pass/fail and accuracy are its. Two products, not a rename.

Lab 06 · where it lives

Twelve lines of CI. That is the gate.

# .github/workflows/evals.yml
on: { pull_request: { paths: ["agent/**", "prompts/**", "evals/**"] }
jobs:
  evals:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -e ".[evals]"
      - run: python -m evals.run --dataset evals/dataset.py --fail-under 0.9
        env:
          OTEL_EXPORTER_OTLP_TRACES_ENDPOINT: ${{ secrets.OTLP_ENDPOINT }}

Note the paths filter: prompt changes trigger the eval suite. Most teams gate code and wave prompts through on a text diff — which is how the 82%-to-64% regression ships.

Six things you take back

From pipe dream to pipeline.

  1. Agents fail quietly. Rate, errors and duration will not show you a confabulation, a quality regression, or a doubled token bill. Span-level GenAI telemetry will.
  2. One vocabulary buys everything downstream. Emit OTel spans with gen_ai.* attributes and the trace tree, the service map, the PPL queries and the evals all work — no vendor agent, no schema translation.
  3. Instrumentation is two lines. register() plus @observe. The agent body you brought in the door is the agent body you leave with.
  4. The pipeline is the unglamorous half, and where the leverage is. Sampling, cardinality and redaction are all decided in the Collector — once, not per agent.
  5. PPL answers the questions you did not plan for. Four verbs, and the loop detector that finds your most expensive failure is seven lines.
  6. Grade the trajectory, not the status code. Golden paths turn "it returned 200" into "it did the right thing, for the right cost".

— Part 01 —

Agents break differently.

A microservice does the same thing every time and fails loudly. An agent chooses what to do at runtime and fails quietly, with a 200 OK and a confident wrong answer.

What one request actually costs you

One question. Dozens of hops.

A single customer turn in the multi-agent travel-planner example: a root agent plans, delegates to a sub-agent, which calls a tool, which calls an MCP server.

invoke_agent · Travel Planner→ chat · planning→ invoke_agent · weather-agent→ invoke_agent · Weather Assistant→ execute_tool · get_current_weather→ tools/call · fetch_weather_api→ POST · /mcp
one POST /plan trace · 37 spans · 2,970 tokens · 1.71 s

Traditional APM records the first box and the total duration. Everything that decided the answer lives in the boxes it never opened.

The core problem

APM treats the agent as a black box.

What APM shows
One fat span
Rate, errors, duration at the request boundary. Exactly right for a service. Blind for an agent, because the interesting decisions are all inside.
What actually happened
A different program each run
Plan, call, read, re-plan, retry, delegate. Sub-agents. Tools. MCP servers. Token spend that swings by an order of magnitude on identical input.
The gap
No shared vocabulary
Without standard attributes for model, tokens, prompts and tool calls, no tool can query across frameworks — and every vendor invents its own schema.
The failure modes RED metrics cannot see

Three ways your agent is already failing.

Failure 01
Confidently wrong
The agent answers from the model instead of calling the tool. Well-formatted, plausible, fiction. Status 200, latency normal.
signal → a trace with chat spans and no execute_tool span
Failure 02
Silently degraded
A prompt edit or model swap drops answer quality. Error rate unchanged. Latency unchanged. A customer tells you next week.
signal → pass rate on a scored dataset, not error rate
Failure 03
Off the golden path
Right answer, wrong route. An extra reasoning loop, a redundant tool call, double the tokens. You find it on the bill.
signal → tool sequence vs golden path; tokens per trace
Measured on the companion repo's committed eval run
22
spans per single customer question

Five support questions produced 110 spans across 5 traces. Of those 110, exactly 10 carried token usage — the chat spans.

That ratio is the whole argument for span-level telemetry: cost lives on a tenth of your spans, and correctness lives on the ones next to them.

— Part 02 —

One vocabulary.
Two stores.

OpenTelemetry GenAI semantic conventions make every framework's agent look the same on the wire — so metrics can live in Prometheus and traces in OpenSearch without you maintaining two mental models.

The shared substrate

Standard gen_ai.* attributes.

A real exported tool span from the companion repo — no custom schema, no translation layer. 

{
 "name": "execute_tool lookup_order",
 "attributes": {
  "gen_ai.operation.name":     "execute_tool",
  "gen_ai.tool.name":          "lookup_order",
  "gen_ai.tool.type":          "function",
  "gen_ai.tool.call.arguments": "{\"order_id\": \"1007\"}",
  "gen_ai.tool.call.result":    "{\"status\": \"shipped\", …}"
 }
}
Spans are indexed as-is with gen_ai.* attributes. No custom schema translation is needed. — Agent Traces documentation
Derived, not configured

Six categories from one attribute.

Agent Traces reads gen_ai.operation.name and maps every span to a category. Categories drive colour, filtering and aggregation across all views — you set the attribute, the UI does the rest.

▸ AGENTinvoke_agent · create_agent ▸ LLMchat ▸ TOOLexecute_tool ▸ CONTENTtext_completion · generate_content ▸ EMBEDDINGSembeddings ▸ RETRIEVALretrieval

Anything without a recognised operation name lands in Other. The practical consequence: a framework has to emit OpenTelemetry spans with GenAI attributes — not merely spans — to show up as agent telemetry.

The detail that makes per-agent PromQL possible

GenAI attributes become Prometheus labels.

Metrics are useless for agents unless you can slice them by agent and by model. One collector flag promotes OTel resource attributes into label names — dots become underscores. 

# otel-collector-config.yaml — the metrics pipeline
exporters:
  prometheus:
    endpoint: 0.0.0.0:8889
    resource_to_telemetry_conversion:
      enabled: true          # ← gen_ai.agent.name → gen_ai_agent_name

# and so this PromQL works, per agent, with no custom metric:
sum(rate(gen_ai_client_operation_duration_count[5m])) by (gen_ai_agent_name)

The stack's own Prometheus configuration goes further and promotes selected gen_ai.* resource attributes over the native OTLP endpoint, which preserves them rather than flattening them on remote write.

— Part 03 —

Instrument your agent.

One call at startup, one decorator on the entry point. The agent body is the code you already had — the framework-specific model and tool calls get traced for you.

Step 01 · Register

One call wires the whole pipeline.

# pip install "opensearch-genai-observability-sdk-py[bedrock]"
from opensearch_genai_observability_sdk_py import register, observe, enrich, score, Op

register(
    endpoint="http://localhost:4318/v1/traces",
    service_name="acme-support-agent",
    # auto_instrument=True by default — discovers installed instrumentors
)
One-line OTEL setup — register() configures the tracer provider, exporter, and auto-instrumentation in one call. — Send Data · AI Agents documentation

Pass the endpoint explicitly. Going to production is this line changing — or just setting OTEL_EXPORTER_OTLP_TRACES_ENDPOINT.

Step 02 · Decorate

Two decorators. Whole run stitched.

# the entry point — one invoke_agent root span per turn
@observe(op=Op.INVOKE_AGENT, name="acme-support-agent")
def handle_support_question(question: str, conversation_id: str = "anonymous") -> str:
    enrich(session_id=conversation_id)   # → gen_ai.conversation.id
    return run_turn(question)          # your existing agent loop, unchanged

# a tool — arguments and return value captured automatically
@observe(op=Op.EXECUTE_TOOL, name="lookup_order")
def lookup_order(order_id: str) -> dict:
    return _ORDERS.get(order_id) or {"error": "order_not_found"}

name= on an INVOKE_AGENT span sets gen_ai.agent.name; on an EXECUTE_TOOL span it sets gen_ai.tool.name. Arguments land in gen_ai.tool.call.arguments, the return value in gen_ai.tool.call.result — that is the span you saw two slides ago.

Ask anything, ad hoc

PPL across every agent span.

The trace store is queryable. Token spend by agent and model, tool failure rate, sub-agent P99 — composed live in the same interface as the trace tree. 

// token spend by agent and model
source = otel-v1-apm-span-*
| where isnotnull(attributes.gen_ai.request.model)
| stats sum(attributes.gen_ai.usage.input_tokens)  as in_tokens,
        sum(attributes.gen_ai.usage.output_tokens) as out_tokens,
        count()                                     as calls
  by attributes.gen_ai.agent.name, attributes.gen_ai.request.model
| sort - out_tokens

// the "looped and hallucinated" case, made visible
source = otel-v1-apm-span-*
| where attributes.gen_ai.operation.name = 'chat'
| stats count() as chat_steps by traceId
| where chat_steps > 3

RED metrics in native PromQL

Rate. Errors. Duration. Per agent.

Real recording rules from the companion repo, over the OpenTelemetry GenAI metric conventions — no bespoke metric names, and gen_ai_agent_name is a label because the collector promoted it. 

# rate — invocations per second, per agent
record: acme:agent_requests:rate5m
expr:   sum(rate(gen_ai_client_operation_duration_count[5m])) by (gen_ai_agent_name)

# errors — error ratio, per agent
record: acme:agent_errors:ratio5m
expr:   sum(rate(gen_ai_client_operation_duration_count{error_type!=""}[5m])) by (gen_ai_agent_name)
      / sum(rate(gen_ai_client_operation_duration_count[5m]))                    by (gen_ai_agent_name)

# duration — p95 latency, per agent
record: acme:agent_latency:p95_5m
expr:   histogram_quantile(0.95,
          sum(rate(gen_ai_client_operation_duration_bucket[5m])) by (le, gen_ai_agent_name))

Two more rules turn these into a burn-rate alert: p95 above 4 s for 5 minutes, and error ratio above 5% for 10 minutes — both severity: page.

— Part 07 —

Grade the agent,
not the status code.

Traces tell you what happened. Evaluation tells you whether it was right — and whether your last prompt change helped or hurt.

Agent Evals · scores as spans

Quality lands in the same trace store.

score() attaches a judgment to the live trace. evaluate() runs a dataset. Benchmark uploads results from an eval library you already use. All of it flows through the same OTLP pipeline. 

# the five criteria this agent is graded on
score(name="answer_correctness", value=correctness)
score(name="right_tool",          value=right_tool)
score(name="trajectory_match",    value=trajectory_match)   # golden path
score(name="latency_ok",          value=latency_ok)
score(name="no_loops",            value=no_loops)

# bring your own library — DeepEval, RAGAS, MLflow, pytest
score(name="deepeval.answer_relevancy", value=value, attributes={
    "gen_ai.evaluation.evaluator.type":  "llm_judge",
    "gen_ai.evaluation.reference_set.id": "acme-golden-dataset-v1",
})

A benchmark nests as test_suite_run → test_case → invoke_agent — so "did v2 regress?" is just another PPL query.

What "correct" means for a non-deterministic program

Define the golden path once.

The trick that makes agent evals cheap: your hardest test cases are the failures already sitting in your trace store. 

@dataclass
class EvalCase:
    question: str
    expected_tool: str                 # the one tool that should be called
    expected_answer_substring: str     # what a correct answer must contain
    golden_trajectory: list[str]       # the expected op/tool sequence

EvalCase(
    question="where is my order #1007?",
    expected_tool="lookup_order",
    expected_answer_substring="shipped",
    golden_trajectory=["invoke_agent", "lookup_order"],
)

A search_policy detour or an extra chat loop is a trajectory mismatch — even when the final answer is right. Three budgets make the rest objective: TOKEN_BUDGET 4000, LATENCY_BUDGET_S 8.0, MAX_CHAT_STEPS 3.

Laptop to production

A config change, not a code change.

The spans and the queries are identical. Only the endpoint and the auth differ — SigV4 instead of basic auth. 

# the only change to your agent: point it at the in-VPC collector
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://otel-collector.internal:4318/v1/traces

# traces on Amazon OpenSearch Service — SigV4, service abbreviation "es"
curl --aws-sigv4 "aws:amz:$REGION:es" -X POST "https://$DOMAIN.es.amazonaws.com/_plugins/_ppl" \
  -d '{"query": "source=otel-v1-apm-span-* | head 20"}'

# metrics on Amazon Managed Service for Prometheus — SigV4, "aps"
curl --aws-sigv4 "aws:amz:$REGION:aps" "https://aps-workspaces.$REGION.amazonaws.com/…/api/v1/query" \
  --data-urlencode 'query=acme:agent_latency:p95_5m'

In OpenSearch UI, AMP is registered as a Prometheus data source with AWS Signature Version 4. The managed deployment uses Amazon OpenSearch Ingestion as the OTLP pipeline in place of the collector and Data Prepper.

Five things to take back

The agent isn't a black box anymore.

  1. Agents fail quietly. Rate, errors and duration will not show you a hallucination, a quality regression, or a doubled token bill. Span-level GenAI telemetry will.
  2. One vocabulary buys everything else. Emit OpenTelemetry spans with gen_ai.* attributes and every framework becomes queryable the same way — no vendor agent, no schema translation.
  3. Two stores, one interface. AMP keeps metrics cheap at high sample rate; Amazon OpenSearch Service keeps unbounded-cardinality spans and logs. They meet on trace ID and service name.
  4. Instrumentation is two lines. register() plus @observe — identical across LangGraph, Strands, AgentCore, Bedrock, OpenAI, Anthropic and Node.
  5. Grade the trajectory, not the status code. Golden paths and scored datasets turn "it returned 200" into "it did the right thing, for the right cost".

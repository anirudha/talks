Why we're here
We kept shipping agents
we couldn't debug.

Traditional APM was built for request → response services. Agents reason, plan, and execute multi-step workflows. Standard metrics and traces don't tell you why an agent made the decision it did. Without that, debugging is guessing.

Here's what we noticed
When you only have inputs and outputs,
debugging an agent means reading prompts and guessing.
When you can see the decision sequence,
debugging becomes a normal engineering task.
Concept · 01

What are agent traces?

The decision sequence the agent actually took. Every prompt, every tool call, every hop between services — each one a span.
Concept · 02

What are agent evals?

Scores on the reasoning path, not just the answer. Offline: benchmark suites you run before shipping. Online: continuous scoring of real traffic.
Our staged approach

Three phases. One loop.

We didn't get here in one step. Every phase has a job, and every phase pays off the next one.

01
Before features
Instrument first
OTel spans for every prompt, tool call, retrieval. Three lines of config, before line one of agent logic.
02
Ready to ship
Evals as a gate
Integration tests for reasoning. Score the decision path. Block the merge when scores regress.
03
In production
Close the loop
Continuous scoring on live traffic. Failed evals → fix → re-ship. Drift caught in hours, not weeks.
Phase 01 · Before the first feature

We instrument before we add features.

Works with any OTel-compatible framework — Strands, LangGraph, CrewAI — and any OTLP-speaking backend (Agent Health, Phoenix, Langfuse, Braintrust). 

# 1. Stand up an OTel-compatible backend
docker compose up -d  # collector + storage + UI

# 2. Point your agent's OTel exporter at the collector
export OTEL_EXPORTER_OTLP_ENDPOINT="http://localhost:4318"

# 3. Run. Every tool call, LLM hop, and retrieval is now a span
python my_agent.py "Why did latency spike at 3am?"
Phase 02 · Ready to ship

Evals as a shipping gate

Integration tests for reasoning. Fails the build when scores regress — the same way unit tests fail when a function does.
Phase 03 · In production

How we close the loop in production.

  • Continuous scoring of live traffic — not just synthetic benchmarks.
  • Support tickets and eval regressions surface degradation before it spreads.
  • The feedback loop: prod trace → failed eval → fix → re-ship.
Scars, not slides

What we got wrong.

Four habits we had to unlearn. The credibility tax for talking about anything that worked.

  • Over-indexed on LLM-as-judge early. Rules and assertions are faster, cheaper, and often sufficient for structured outputs.
  • Stored evals separately from traces. Correlating them by hand became unsustainable around eval #50.
  • Wrote vague rubrics. "Is the answer helpful?" gives noisy judges. Specific rubrics give signal.
  • Didn't budget for cardinality. Agent traces generate a lot of spans. Sample intentionally — or your storage bill will teach you.
One bug, one trace

The conversation history bug.

An agent we were building. Answers looked fine. Cost didn't.

  • SymptomToken usage climbed quadratically with every conversation turn.
  • Without tracingLatency and cost both up. Outputs unchanged. No obvious cause.
  • In the traceThe full conversation history was re-sent on every LLM call.
  • The fixProper memory — summarization plus sliding window. Token usage flattened to linear.

The fix was easy. The harder part was noticing.

Getting started

How we started.

  1. OTel traces. No evals yet. Just see what the agent is doing.
  2. 5 eval cases from real queries. Written as code. Scored by hand.
  3. LLM-as-judge. Run on every PR. Block merges that drop scores.
  4. Online evals. Expand coverage. Catch drift on live traffic.

Pick one tool and start: Agent Health, Phoenix, Braintrust, Langfuse. Anything that speaks OTel. The UI is the view — version-control your eval suite in git.
